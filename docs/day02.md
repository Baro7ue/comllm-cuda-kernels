# 第 2 天：写第一个算子——矩阵乘

第 1 天的结论：时间的 71% 在矩阵乘，其中 gate 和 up 两个内核就占 36%。所以从它写起。
文件分工：`cuda/01_matmul/my_kernels.cuh` 是你写的内核，`ref_kernels.cuh` 是参考答案，`matmul.cu` 是测试框架。标记同前：【实测】【估算】【推测】。

## 1. 这个算子要算什么

三块数据，大小和模型里的 gate 一样：

| 名字 | 形状 | 含义 | 大小 |
|---|---|---|---:|
| X | 145 行 × 896 列 | 输入。每行是一个 token | 0.52 MB |
| W | 4864 行 × 896 列 | 权重。每行是"算出一个输出要用的 896 个权重" | 17.4 MB |
| Y | 145 行 × 4864 列 | 输出。每行是一个 token 的 4864 个结果 | 2.82 MB |

规则只有一条：

```
Y[n][m] = X[n][0]×W[m][0] + X[n][1]×W[m][1] + … + X[n][895]×W[m][895]
```

也就是：第 n 个 token 的第 m 个输出 = X 的第 n 行和 W 的第 m 行，对应位置相乘再全部加起来。
Y 里有 145×4864 ≈ 70 万个数，每个要做 896 次乘和 896 次加，一共 1.264×10⁹ 次运算。

这一版三块数据全用 float（32 位浮点）。真实的模型里 W 是 8 位整数（Q8_0），那是后面的事：
先把"怎么组织计算"弄对，再换数据类型。

内存里怎么放：二维表在内存里是一长条，一行接一行。所以 X 的第 n 行第 k 个数在 `X[n*K + k]`，
W 的第 m 行从 `W + m*K` 开始。代码里的下标都是这么来的。

## 2. 练习 1：每个线程算一个数（你来写）

最直接的想法：Y 有 70 万个数，那就开 70 万个线程，一人算一个。

线程排成一个二维的网格：纵向 145 排（每排对应一个 token），横向若干块、每块 256 个线程，
合起来盖住 4864 个输出。每个线程从自己的位置算出 n 和 m，就知道该算 Y 里的哪个数。

**怎么练习：**

1. 打开 `cuda/01_matmul/my_kernels.cuh`，按里面的第 1–5 步把代码补上。
2. 在 Mac 上运行 `bash scripts/board.sh`。它把代码传到板子、编译、运行，打印一张表。
3. "练习 1（你写的）"那行显示"通过"就对了。显示"失败"时，表下面会说第一个错在哪个位置、
   你的值和准确值各是多少。编译不过时，终端里会有带行号的报错。

参考答案在 `cuda/01_matmul/ref_kernels.cuh`，卡住了再看。

## 3. 怎么判断"算对了"

矩阵乘和第 1 天的加法不一样：加法只算一步，CPU 和 GPU 的结果逐位相同；
矩阵乘要把 896 项累加起来，float 每加一次都可能舍入一次，所以 GPU 的结果和"准确值"会差一点点，
而且累加顺序不同，差的也不同。**不能要求逐位相同，要定一个有依据的容许误差。**

做法：
1. 在 CPU 上用 double（64 位）算一遍，当作准确值。
2. 对每个输出同时算 S = 896 项的绝对值之和。
3. 数值分析给出 float 累加的最坏情况：|算出来的 − 准确值| ≤ K × 2⁻²⁴ × S，这里约为 5.3×10⁻⁵ × S。
4. 70 万个输出逐个检查。有一个超过这个界，就判失败。

超过这个界的误差，舍入解释不了，只能是程序写错了（比如下标算错、漏写了某个元素）。
每一版开始前框架会把 Y 清零，所以漏写的元素一定会被查出来。

## 5. 为什么这么慢

回到第 1 天的那句话：**一个权重读进来以后，145 个 token 每个都要用它算一次。读一次、算 145 次。**

v1 没做到这一点。算 Y[0][m] 的线程把 W 的第 m 行读了一遍；算 Y[1][m] 的是另一个线程，
它又把同一行从头读了一遍……145 个 token 就读了 145 遍。

- W 只有 17.4 MB，但 v1 实际读了 145 × 17.4 MB ≈ **2.5 GB**。
- 第 1 天量到的内存带宽是 61 GB/s，光搬这 2.5 GB 就要约 41 ms。【估算】
- 再加上读法也不好：相邻两个线程读的是 W 里相邻的两**行**，地址隔着 3.6 KB，
  硬件没法把一组线程的读取合并成一整段。

所以 v1 的 80 ms 几乎全花在重复搬数据上，GPU 的算力大部分时间在等数据。
它本该是"受算力限制"的算子，被写成了"受带宽限制"。

## 6. 练习 2：一个线程算 4 个 token【实测】

思路：一个线程负责"第 m 个输出、连续 4 个 token"，手里拿 4 个累加器。
每读进一个权重，就和 4 个 token 的输入各乘一次。W 的每一行被读的遍数从 145 降到 37。

写的时候反复用到的一条规律：**换行就要乘上每行的长度**。X 和 W 每行 K 个数，Y 每行 M 个数。
`x[t*K + i]` 是"跳过 t 整行，再数 i 个"；`Y[(n0+t)*M + m]` 是"跳过 n0+t 整行，再数 m 个"。

边界：145 = 36×4 + 1，最后一排只有 1 个真 token，用 `cnt = min(4, N - n0)` 挡住另外 3 个。

参考 v2 首次运行在 `results/2026-11-15/matmul_v2_ref.txt`。

| 版本 | 正确性 | 最大误差 ÷ S | 中位数 | 相对 v1 |
|---|---|---:|---:|---:|
| 练习 1：每线程 1 个 token | 通过 | 2.75×10⁻⁷ | 80.4 ms | 1× |
| 练习 2（自己写的）：每线程 4 个 | 通过 | 2.75×10⁻⁷ | **22.6 ms** | 3.6× |
| 参考 v2：每线程 4 个 | 通过 | 2.75×10⁻⁷ | 22.6 ms | 3.6× |

- 现在每个线程把 X 的同一段也各读一遍（同一排的 4864 个线程读的是同样的 4 行 X）；
- 相邻线程读的 W 地址仍隔着 3.6 KB，读取合并不了。

### 一次没有应验的预测

用 4、8、16 三档拟合"时间 ≈ 固定部分 + 可变部分 ÷ 每线程 token 数"，得到约 7.4 ms + 59 ms ÷ T，
据此预测 32 个 token 时约 9.2 ms。【估算】

实测（2026-11-16，用户运行，`TOKENS_PER_THREAD = 32`）：**11.56 ms**，通过，误差 2.75×10⁻⁷。
同一次运行里参考 v2 的 16 个 token 是 11.66 ms；16 个 token 这一档在各次运行里是 11.1–11.8 ms。

结论：32 和 16 没有可分辨的差别，预测不成立。时间在 11 ms 左右就不再下降，而不是模型说的 7.4 ms。
三个点拟合出来的简单模型，外推一档就错了。原因没有量过。【推测】可能是 32 个累加器放不进寄存器。

## 8. 练习 3：共享内存，朴素写法

这里暂时退回练习 1 的分工（一个线程算一格），单独学共享内存；之后在练习 4 里和练习 2 合并。
几个练习的关系（2026-11-21 补，用户指出教程原来没交代这一点）：

| | 数据直接从内存读 | 数据先搬进共享内存 |
|---|---|---|
| 一个线程算 Y 的 1 格 | 练习 1 | 练习 3 |
| 一个线程算 Y 的同一列、多行 | 练习 2 | 练习 4（参考 v4） |

练习 1 → 2 改的是"一个线程算多少"，练习 1 → 3 改的是"数据从哪里取"，练习 4 是两者合并。

### 8.1 为什么要它

练习 2 里，同一排的 4864 个线程负责的 token 相同、输出不同。它们读的 W 各不相同，
但读的 X 完全一样：同样的几十行 X 被每个线程各读了一遍。
共享内存用来处理这类重复：一组线程把数据从内存取一次，放到组里人人能拿到的地方。

三种存放数据的地方：

| 位置 | 例子 | 谁能用 | 快慢 |
|---|---|---|---|
| 寄存器 | `acc`、`m` 这些局部变量 | 只有这个线程 | 最快 |
| 共享内存 | `__shared__ float sX[16][16]` | 同一个线程块里的线程 | 快 |
| 内存 | `X`、`W`、`Y` | 所有线程 | 慢 |

### 8.2 线程怎么排

一个块是 16 × 16 的方阵（`dim3(TILE, TILE)`），负责 Y 的一个 16 × 16 小方格，每个线程算一个 Y[n][m]。
`threadIdx.y` 是块内第几行。

```
tx = threadIdx.x        ty = threadIdx.y
m0 = TILE * blockIdx.x  n0 = TILE * blockIdx.y
m  = m0 + tx            n  = n0 + ty
```

真实尺寸下横向 4864 ÷ 16 = 304 块，纵向 145 ÷ 16 向上取整 = 10 排。

### 8.3 每一段做四件事

896 个特征切成 56 段，每段 16 个，`k0` 是这一段的第一个特征。

1. 搬：线程 (tx, ty) 搬两个数。`sX[ty][tx]` ← token n 的第 k0+tx 个特征；
   `sW[ty][tx]` ← 输出 m0+ty 的第 k0+tx 个权重。不存在的行放 0。
2. `__syncthreads()`：等全块搬完。
3. 算：`acc += sX[ty][kk] * sW[tx][kk]`，kk 从 0 到 15。
4. `__syncthreads()`：等全块算完，才能进下一段覆盖小表。

56 段都做完后，n 和 m 都在范围内的线程才写 `Y[n*M + m]`。

### 8.4 写的时候出过的错（都值得记）

| 写成了 | 应该是 | 道理 |
|---|---|---|
| `sX[ty][tx] = X + n*K + (k0+tx)` | `X[n*K + (k0+tx)]` | 加法得到的是地址；方括号才把数取出来 |
| 搬 W 时行号用 `m` | `m0 + ty` | `m = m0 + tx`，输出和特征都由 tx 决定，只搬了 16 个不同的数。搬满 16 × 16 要两个独立的序号 |
| `kk < TILE - 1` | `kk < TILE` | `<` 后面写个数，不用减 1（练习 2 的 `t < cnt - 1` 是同一个错） |
| `sX[n][kk]`、`sX[n0][kk]` | `sX[ty][kk]` | 小表只有 16 行，只认块内序号 tx、ty；真实编号 n、m 用在 X、W、Y 上 |
| `Y[n][m] = acc` 写在循环里 | 循环外 `if (n < N && m < M) Y[n*M + m] = acc;` | 56 段算完才写；Y 是地址，只能用一长条的下标；越界线程不写 |
| 块数的除数用 256 和 `TOKENS_PER_THREAD` | 都用 `TILE` | 除数是"一个块在这个方向上盖多少个"，这里横竖都是 16 |
| Y[64][47] | Y[47][64] | Y 的写法是 Y[n][m]，token 在前 |

两条和练习 1、2 不同的规矩：
- 越界的线程不能提前 `return`。别的线程要用它搬的数，而且它走了别人在集合点等不到它。
- 搬数据时的分工和"我最后算哪个 Y"无关。线程 (tx, ty) 算的是输出 m0+tx，搬的却是输出 m0+ty 的权重。
  所以搬的时候 `sW` 的行号是 ty，用的时候是 tx。

说明：3c 的行号、第 4 步、第 5 步这三处最后是看了答案改的，其余是自己写的。

### 8.6 为什么慢【推测】

没有用工具量过，下面是按硬件的工作方式推的。

- 线程每 32 个一组同时执行同一行代码。16 × 16 的块里，一组是相邻两行（ty 两个值，tx 从 0 到 15）。
- 共享内存有 32 个取数窗口（bank），窗口号 = 位置 ÷ 32 的余数。
  一组线程同时取数时，同一个窗口里的不同位置要排队；同一个位置可以共用。
- `sW[tx][kk]` 的位置是 `tx*16 + kk`。固定 kk，tx 从 0 到 15 得到 16 个不同位置，
  只落在 2 个窗口上，每个窗口 8 个位置排队。这一行每个线程要执行 896 次。
- `sX[ty][kk]` 没有这个问题：一组里 ty 只有两个值，大家要的是同样的两个位置。

对策：把 `sW` 转个方向存（存 `sW[tx][ty]`，读 `sW[kk][tx]`），读的时候位置是 `kk*16 + tx`，
连续 16 个，落在 16 个不同窗口上。参考答案这样改后是 6.68 ms。

进度（2026-11-18）：练习 3 朴素版通过。
（2026-11-21 改计划：不回头改练习 3 的 `sW`，直接做练习 4；bank 冲突放到练习 4c 讲，这里的 13.7 / 6.7 ms 当第二个例子。）

和练习 2 相比只改了一样：X 先由全块搬进 `sX`，再从 `sX` 里取。时间少了约 27%。
上板前没有写下预测（问了三次，没有答），所以这次没有"预测对不对"可记。

核心的一行：

```cpp
acc[t] += sX[t][kk] * w[k0 + kk];
```

`sX` 是小表，只用局部序号 t、kk；`w` 指向大表 W 的一行，列号要带起点 k0。两者取的是同一个特征。

写的时候出过的错：

| 写成了 | 应该是 | 道理 |
|---|---|---|
| `__syncthreads()` 写在 `k0` 循环外面 | 循环里面，搬完之后 | `sX` 只有一段的大小，下一圈就被盖掉；每一段都要完整走一遍搬、等、算、等 |
| 循环变量叫 `i`，循环体里用 `kk` | 统一叫 `kk` | 没定义的名字编译不过 |
| `kk < SEG - 1` | `kk < SEG` | 第三次出现（练习 2、练习 3 各一次）：`<` 后面写个数，不减 1 |
| `sX[n0 + t][k0 + kk]` | `sX[t][kk]` | 小表不带起点；起点在搬的那一步已经用掉了 |
| `sX[n0 + ty][k0 + tx]` | `sX[t][kk]` | ty、tx 是搬的时候的固定岗位；算的时候要跑遍整张小表，用循环变量 |
| 算的部分没有包 `if (m < M)` | 包上 | 越界线程不再提前 return，要自己挡住对 W 的读 |
| 写回时 `if (n < M)` | `if (m < M)` | 笔误，这个内核里没有 n |

说明：`sX[t][kk]` 这一行最后是看了答案改的；第 2 步的 `ty = tid / SEG`、`tx = tid % SEG`，
3a 的搬运和边界判断，是自己一次写对的。

## 10. 更早写的方向说明

让每个权重只从内存读一次，然后给所有 token 用。办法是分块（tiling）：
一个线程块先把一小块 W 和一小块 X 搬进自己的**共享内存**（每个线程块自带的一小块高速存储，
在芯片内部，读它比读内存快得多），块里的线程再反复用这份数据算出一小块 Y。

llama.cpp 的 `mul_mat_q` 也是这个思路，第 1 天看到的"每 128 个 token 一组"多半就是它的块大小【推测】。
