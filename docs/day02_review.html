1　要算的东西：Y = X · Wᵀ

三块数据，大小照的是 Qwen2.5-0.5B 每层前馈网络里的 gate 矩阵乘（896 → 4864）。练习里的数是测试框架随机造的，只用来检查"算得对不对、快不快"。

名字形状是什么大小
X145 × 896输入：145 个 token，每个 896 个数。上一步算出来的数据，每次请求都不同0.52 MB
W4864 × 896权重：模型参数，训练时定好，推理时只读。每一行是"算出一个输出要用的 896 个权重"17.4 MB
Y145 × 4864输出：要求的东西。每个 token 得到 4864 个数2.82 MB

内存里二维表是一长条，一行接一行。所以第 n 行第 k 个数在 X[n*K + k]，W 的第 m 行从 W + m*K 开始，Y 的第 n 行第 m 个在 Y[n*M + m]。规律只有一条：换行就乘上每行的长度。X、W 每行 K = 896 个，Y 每行 M = 4864 个。

本页的行和列

下面说"行""列"时都带上是哪个矩阵的。最常用的是 Y：

Y 的编号代表CUDA 里管它的
行（共 145 行）ntokenblockIdx.y、threadIdx.y（ty）
列（共 4864 列）m输出blockIdx.x、threadIdx.x（tx）

一句话记：x 管列，y 管行。顺序容易乱：矩阵先写行再写列，Y[n][m] 是 Y[行][列]；CUDA 的 dim3(x, y) 却先写列再写行，所以 grid(19, 145) 是"19 个列块、145 个行块"。还有一处：W 的第 m 行，算出来的是 Y 的第 m 列，因为 Y = X · Wᵀ 里转置把 W 的行变成了列。

出发点：W 里同一行，145 个 token 每个都要用一次。读一次，能用 145 次。三个练习都在想办法兑现这句话。

2　一条主线：同一个权重，从内存读了几遍

三种存放数据的地方，越往下越快、越小、能用它的人越少：

位置代码里的样子谁能用这块板子上
内存X、W、Y所有线程7.91 GB，有效带宽 61.1 GB/s 实测
共享内存__shared__ float sW[16][16]同一个线程块每个 SM 164 KB，每块默认最多 48 KB 实测
寄存器acc、wk、m 这些局部变量只有这个线程每个 SM 65536 个 实测

3　练习 1：每个线程算 Y 的一格

分工：Y 有 145 × 4864 ≈ 70 万格，就开 70 万个线程，一人一格。一个块是 256 个线程，盖住 Y 的 1 行 × 256 列。Y 的列方向要 4864 ÷ 256 = 19 块，行方向要 145 块，所以 grid(19, 145)：先写列块数，再写行块数。

__global__ void my_v1_kernel(const float* X, const float* W, float* Y, int N, int K, int M) {
    const int m = blockIdx.x * blockDim.x + threadIdx.x;   // Y 的第几列（输出）
    const int n = blockIdx.y;                              // Y 的第几行（token）
    if (m >= M) return;                                    // 多出来的线程没活干
    const float* x = X + n * K;                            // X 的第 n 行
    const float* w = W + m * K;                            // W 的第 m 行
    float acc = 0.0f;
    for (int k = 0; k < K; ++k) acc += x[k] * w[k];
    Y[n * M + m] = acc;
}
// 发起：grid(⌈M / 256⌉, N)，每块 256 个线程

线程数怎么来：先定"一个线程负责什么"，线程总数等于活的份数。每块 256 个是手选的：要是 32 的倍数（一个 warp 是 32 个线程），不能超过 1024。v1 里同块的线程互不配合，换成 128 或 512 速度差别应该很小，这一点没测过。

结果：通过，80.3 ms 实测。

为什么慢：算 Y[0][m] 的线程把 W 第 m 行读了一遍，算 Y[1][m] 的是另一个线程，又读了一遍。145 个 token 就读 145 遍，合计约 145 × 17.4 MB ≈ 2.5 GB，按 61.1 GB/s 光搬这些就要约 41 ms 估算。另外相邻线程读的是 W 里相邻两行，地址隔着 896 × 4 = 3.6 KB，硬件没法把一组线程的读取合成一整段。

4　练习 2：一个线程算同一个输出的 T 个 token

分工：一个线程负责"第 m 个输出、连续 T 个 token"，手里拿 T 个累加器。每读进一个权重，就和 T 个 token 的输入各乘一次。列方向和练习 1 一样，每块 256 列；行方向从每块 1 行，变成每块 T 行。所以一个块盖住 Y 的 T 行 × 256 列，grid(19, ⌈145 ÷ T⌉)。

const int n0  = TOKENS_PER_THREAD * blockIdx.y;            // 我这个行块的第一行（token）
const int cnt = min(TOKENS_PER_THREAD, N - n0);           // 最后一个行块可能不满 T 行
float acc[TOKENS_PER_THREAD] = {0.0f};
for (int i = 0; i < K; ++i)
    for (int t = 0; t < cnt; ++t)
        acc[t] += x[K*t + i] * w[i];                        // 跳过 t 整行，再数 i 个
for (int t = 0; t < cnt; ++t) Y[(n0 + t)*M + m] = acc[t];

边界：145 = 36 × 4 + 1，T = 4 时最后一个行块只有 1 行是真的 token，另外 3 行用 cnt 挡住，不读也不写。

读到的东西：T 越大，W 从内存读的遍数越少，时间先快速下降，到 16 左右就不降了。T = 32 时 W 只读 5 遍，约 87 MB，按带宽算约 1.4 ms 估算，实测却是 11.6 ms。说明这时 W 的流量已经不是瓶颈，时间花在别处。可能是同一个行块里负责 Y 4864 列的 4864 个线程，把同样的 T 行 X 各读了一遍，也可能是 32 个累加器放不进寄存器 推测。

练习 2 的一句话：把一个权重读进寄存器，连用 T 次。三个点拟合出来的模型，外推一档就错了，所以每个结论都要量过才算数。

5　练习 3：一个线程块合作算 Y 的一个 16 × 16 小块

为什么要它：练习 2 里同一个行块的线程负责 Y 的同样几行（同样的 token），读的 X 一模一样，每个线程各读一遍。共享内存处理的就是这种重复：一组线程把数据从内存取一次，放到组里人人能拿的地方。

分工：一个块是 16 × 16 = 256 个线程，负责 Y 的一个 16 × 16 小块，每个线程仍然算一格。896 个特征切成 56 段，每段 16 个。每一段做四件事：全块一起搬、等齐、各自算、再等齐。Y 的列方向要 4864 ÷ 16 = 304 块，行方向要 ⌈145 ÷ 16⌉ = 10 块，grid(304, 10)。块里 tx 管 Y 的列（输出 m），ty 管 Y 的行（token n）。

三条规矩

规矩为什么
大表用真实编号，小表用块内序号X、W、Y 在内存里，用 n、m、k0 + tx；sX、sW 只有 16 × 16，只认 tx、ty、kk
搬的和用的不是同一行搬是全块分工：每格有且只有一个人搬，按 ty 定行、tx 定列。算是各取所需：线程要的 sW 行是 tx。tx 相邻的线程读 W 同一行里相邻的数，地址连着，硬件能合并
越界的线程不能提前 return别的线程要用它搬的数（越界就放 0），而且它走了，别人在 __syncthreads() 等不到它。它只是最后不写 Y

变量名的规律

样子含义例子
带 0起点：这个块、这一段的第一个n0、m0、k0
t 开头，或字母重复块内、段内第几个（0 到 15）tx、ty、kk
单个字母在整张大表里的真实编号n、m

它们的关系永远是：真实编号 = 起点 + 局部序号。n = n0 + ty，m = m0 + tx，特征 = k0 + kk。写下标前先问一句"这是大表还是小表"。

结果：通过，13.66 ms，和参考的朴素版 13.65 ms 一样 实测。用了共享内存，反而比练习 2 慢。

6　练习 3 为什么反而慢：共享内存的取数窗口

对比一下：参考 v2（每线程 16 个 token）的 W 也是读 10 遍，11.2 ms；练习 3 是 13.7 ms。只把 sW 的两个下标对调的版本是 6.7 ms 实测。从内存读的量一样，差别在共享内存里怎么取。

共享内存有 32 个取数窗口，叫 bank。第几个窗口 = 位置 ÷ 32 的余数（位置按 float 数）。一组 32 个线程（一个 warp）同时取数时，落在同一个窗口里的不同位置要排队，同一个位置可以共用。16 × 16 的块里，一个 warp 是块里相邻的两行线程，对应 Y 小块的两行：ty 两个值，每行 tx 从 0 到 15。

存法读（每段 16 次）写（每段 1 次）实测时间
朴素 sW[ty][tx] 写，sW[tx][kk] 读排 8 轮1 轮13.7 ms
转置 sW[tx][ty] 写，sW[kk][tx] 读1 轮排 8 轮6.7 ms

轮数是按硬件规则算出来的，时间是实测。"慢在 bank 冲突"这个归因还没有用分析工具量过 推测。sX[ty][kk] 没有这个问题：一个 warp 里 ty 只有两个值，大家要的是同样的两个位置，可以共用。

练习 3 的一句话：用了共享内存不等于变快。数据在共享内存里怎么摆，决定一组线程取数时要不要排队。

7　到现在为止的全部结果

正确性的判断方法：CPU 上用 double 算准确值，再对每个输出算 S = 896 项绝对值之和。float 累加 K 项的最坏误差是 K × 2⁻²⁴ × S ≈ 5.3 × 10⁻⁵ × S。70 万个输出里有一个超过这个界，就不是舍入能解释的，一定是程序写错了。

9　回忆题

先不看代码，凭记忆答，答完再展开对答案。前四题按真实的 TILE = 16。

1　线程 (tx = 3, ty = 5)，所在块 blockIdx.x = 2、blockIdx.y = 1，现在 k0 = 32。它负责 Y 的哪一格？这一轮搬哪两个数？
m0 = 2 × 16 = 32，n0 = 1 × 16 = 16；m = 32 + 3 = 35，n = 16 + 5 = 21，负责 Y 的第 21 行第 35 列，即 Y[21][35]。
搬 sX[5][3] ← X[21][35]（token n 的第 k0 + tx = 35 个特征）；
搬 sW[5][3] ← W[37][35]（输出 m0 + ty = 37 的第 35 个权重）。注意它搬的是输出 37，不是自己的输出 35。
2　接上题，它算的时候读 sW 的哪一行？那一行是哪些线程搬进来的？
读 sW 第 tx = 3 行，即 sW[3][kk] = W[35][32 + kk]。这一行是 ty = 3 的那 16 个线程（tx = 0 到 15）搬的。
3　第二个 __syncthreads() 去掉会出什么问题？
快的线程会进入下一段，把新数据写进 sX、sW，而慢的线程还在用旧数据算这一段，结果就错了。这种错可能时有时无，不一定每次都能复现，所以更难查。
4　M = 5000 时练习 3 在 Y 的列方向要几块？多出来的线程做什么，和练习 1 有什么不同？
⌈5000 ÷ 16⌉ = 313 块。最后一个列块 m0 = 4992，盖住 Y 的第 4992–5007 列，tx ≥ 8 的线程 m ≥ 5000。
它们照样搬数：sX 那一格是真实的 X；sW 那一格看 m0 + ty，ty < 8 时搬真实的 W，ty ≥ 8 时放 0。它们照样走到两个 __syncthreads()，只是最后不写 Y。练习 1 里这种线程一开始就 return。
5　练习 2 设每线程 32 个 token 时，Y 的行方向要几块？最后一个行块里几行是真的 token？W 的每一行从内存读几遍？
⌈145 ÷ 32⌉ = 5 个行块；最后一个行块从 Y 的第 128 行开始，有 145 − 128 = 17 行是真的 token；W 的每一行被 5 个行块各读一遍，共 5 遍。
6　练习 3 用了共享内存，为什么比练习 2 慢？怎么改？
朴素存法下，一个 warp 读 sW[tx][kk] 时 16 个位置挤在 2 个窗口上，每次要排 8 轮，这一行每个线程执行 896 次 推测。改法：搬的时候存成 sW[tx][ty]，算的时候读 sW[kk][tx]。参考答案这样改后是 6.7 ms。
