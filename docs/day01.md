## 1. 先认几个词

- **张量**：一块按形状排好的数。比如"145 个 token，每个 896 个数"就是形状 145×896 的张量。
- **算子（operator）**：对张量做的一步运算，输入几个张量，输出一个张量。矩阵乘、加法、归一化都是算子。
  模型的一次计算就是几百个算子按固定顺序一个接一个地执行。
- **内核（kernel）**：GPU 上实际执行的那段函数。一个算子通常对应一个内核（有时两三个）。
  "写 CUDA 算子"说的就是写这段函数，以及在 CPU 端准备数据、发起它的代码。
- **前向（forward）**：从输入 token 算到输出概率的整个过程。读提示词 = 对一批 token 做一次前向。
- **KV 缓存 / 前缀缓存**：每个 token 在每一层都会算出一对向量（K 和 V），后面的 token 要用到。
  算过的存起来，下次提示词开头相同的部分就不用重算。你的部署里 278 个 token 有 133 个是这样省掉的。

## 2. 这个模型一次前向有哪些算子

Qwen2.5-0.5B 的结构（出处：模型的 config.json）：每个 token 用 d = 896 个数表示；24 层；
每层的前馈网络中间宽度 4864；注意力 14 个头，每头 64 维；K、V 只有 2 个头（128 维）；词表 151936。

设要算 N 个新 token，一层里依次发生这些事（括号里是输出形状）：

```
x (N×896)
 ├─ RMSNorm ─────────────────────────────── (N×896)    归一化：每行除以自己的均方根
 ├─ 矩阵乘 q_proj  896→896  + 偏置 ───────── (N×896)    ┐
 ├─ 矩阵乘 k_proj  896→128  + 偏置 ───────── (N×128)    ├ 三个"线性层"：每行乘一个权重矩阵
 ├─ 矩阵乘 v_proj  896→128  + 偏置 ───────── (N×128)    ┘
 ├─ RoPE（q 和 k）──────────────────────────           按位置旋转，让模型知道谁在前谁在后
 ├─ 把 k、v 写进 KV 缓存
 ├─ 注意力：每个新 token 的 q 和它之前所有 token 的 k 算相似度，按相似度把 v 加权求和 (N×896)
 ├─ 矩阵乘 o_proj  896→896 ──────────────── (N×896)
 ├─ 加回 x（残差）
 ├─ RMSNorm
 ├─ 矩阵乘 gate    896→4864 ─────────────── (N×4864)   ┐
 ├─ 矩阵乘 up      896→4864 ─────────────── (N×4864)   ├ 前馈网络（FFN）
 ├─ SwiGLU：silu(gate) × up ─────────────── (N×4864)   │
 ├─ 矩阵乘 down    4864→896 ─────────────── (N×896)    ┘
 └─ 加回（残差）
```

一层 7 个矩阵乘。24 层之后，只取最后一个 token，再做一次 RMSNorm 和一个 896→151936 的矩阵乘（lm_head），
得到词表上每个词的分数。你的调度器只要这一个 token 的分数，所以"生成"几乎不花时间。

按 `tools/model_math.py` 的数法，一次前向一共 628 个小步骤【估算，实际个数以 nsys 记到的为准】。

## 3. 一个算子要多久：两个量决定下限

算子做的事只有两类：**算**（乘、加）和**搬**（把数从内存读进来、把结果写回去）。所以它至少要花

```
下限时间 = max( 计算量 ÷ 硬件每秒能算多少 ,  读写的字节数 ÷ 内存每秒能搬多少 )
```

哪一项大，这个算子就"受哪一项限制"。这个简单模型叫 roofline。它给的是下限：实际一定更慢，
但差多少、差在哪，正是后面优化要找的东西。

- **矩阵乘**：N 行、每行 k 个数，乘一个 k×m 的权重，要做 N×k×m 次乘法和同样多次加法。
  例：gate，N=145，k=896，m=4864 → 2×145×896×4864 ≈ 1.26×10⁹ 次运算。它是"算"的大头。
- **加法、归一化、激活函数**：每个数只算一两次，计算量很小，时间几乎全在"搬"。

硬件能力【估算，按规格推，待板子上核对】：Orin Nano 的 GPU 有 8 个 SM（可以理解成 8 个小处理器，
每个 128 个核），MAXN_SUPER 下最高 1020 MHz；内存是和 CPU 共用的 LPDDR5，理论带宽 102.4 GB/s。
Q8_0 的权重是 8 位整数，llama.cpp 用一条叫 dp4a 的指令（一次做 4 个 int8 乘加）来算
【凭印象，待在板子上读 `ggml-cuda/mmq.cuh` 核对】，折合约 8.4×10¹² 次运算/秒。

> **更正（2026-11-19 核对，11-21 补记）**：上面关于 dp4a 的说法是错的。在 5aeac37a3、sm_87 上，
> llama.cpp 的 Q8_0 `mul_mat_q` 用的是 int8 张量核（机器码里是 IMMA 指令，没有 dp4a）。
> 详见 `docs/day01_results.md` 第 4 节末尾和 `results/2026-11-19/mmq_mma_check.txt`。

## 4. GPU 是怎么执行一个内核的

看 `cuda/00_hello/vector_add.cu`，它做的是 c[i] = a[i] + b[i]，带详细注释。要点：

- CPU 端调用 `vector_add<<<块数, 每块线程数>>>(...)`，这叫**发起**内核。
  GPU 会启动 块数×每块线程数 个线程，**每个线程都执行同一段函数**。
- 线程靠 `blockIdx`（我在第几块）和 `threadIdx`（我是块里第几个）算出"我该处理第几个元素"。
  没有 for 循环遍历全部元素——并行就是靠"每个线程认领自己的那几个"实现的。
- 线程按 32 个一组执行，这一组叫 **warp**。同一个 warp 里的线程如果读的是相邻地址，
  硬件能把 32 次读合成一整段，这是搬数据快不快的关键。
- 发起是异步的：CPU 发完就往下走，不等 GPU 算完。所以计时不能用 CPU 的秒表，
  要么先 `cudaDeviceSynchronize()` 等 GPU 算完，要么用 CUDA 事件（程序里用的是后者）。
- Jetson 上 CPU 和 GPU 共用同一块内存，但 `cudaMemcpy` 仍然是一次真拷贝。

这个程序顺带量出板子的**有效内存带宽**：384 MB 的数据搬一遍要多久。量出来以后用它替换估算里的
102.4 GB/s（`model_math.py --bw-gbs <实测值>`），估算表就更可信一些。

## 5. 怎么量：三把尺子

| 尺子 | 量什么 | 工具 | 特点 |
|---|---|---|---|
| A. llama-bench | 读 N 个 token 的总时间 | `scripts/bench_baseline.sh` | 最准的总数；不分算子 |
| B. nsys | 每个 GPU 内核的起止时刻 | `scripts/profile_nsys.sh` + `tools/nsys_summary.py` | 不改 llama.cpp；按算子类别分；记录有开销，看比例不看绝对值 |
| C. 逐节点同步计时 | 每一层每个算子的时间 | 给 llama.cpp 打一个小补丁 | 【计划】能分到"第几层的哪个算子"；要先在板子上读源码再写 |

上板后发现：llama.cpp 从第二趟起把整趟前向打包成一个 CUDA graph 一次发起，nsys 默认把整张 graph 记成一条。
`profile_nsys.sh` 现在加了 `--cuda-graph-trace=node`，让它进到 graph 里逐个内核记。

为什么 B 不能直接分层：nsys 只知道内核的名字（比如 `mul_mat_q`），不知道它属于第几层。
`nsys_summary.py` 先按时间上的空隙把内核切成一趟一趟的前向，再按名字归类。
它有一个自检：每趟的内核个数应该相同，不同就说明切错了。

B 的表里有两个时间要分清：**GPU 忙碌时间**（各内核自己的时长之和）和**墙上时间**（一趟从头到尾）。
墙上 − 忙碌 = GPU 在等 CPU 发下一个内核。这部分再怎么优化单个算子也减不掉，要靠少发内核（算子融合）。

```

```

```bash

```

```bash
N=145 D=133 bash scripts/profile_nsys.sh
```

每一步看什么：

1. `env_check.sh`：L4T R39.2.1、nvcc 13.2、llama.cpp 5aeac37a3、电源模式 MAXN_SUPER 是否和记录一致；
   GPU 当前频率是多少；有没有别的 llama 进程；nsys 装了没有；部署日志里 flash attention 是开是关。
2. `vector_add`：正确性那行必须是"通过"；记下 SM 个数、频率、有效带宽。
3. `bench_baseline.sh`：`-p 145 -d 133` 那行的 p50 应该接近 44 ms，`-p 278` 接近 68 ms。
   差很多就先找原因（频率、flash attention 设置、llama-bench 和 llama-server 的差别），不往下走。
4. `profile_nsys.sh`：得到第一张实测分布表，填到第 7 节。

带缓存的那次（D=133），llama-bench 每轮会先读 133 个再读 145 个，两趟交替。汇总时用
`python3 tools/nsys_summary.py <文件>.sqlite --every 2 --offset 1` 只看后一趟；先看切段表确认是这个顺序。

把结果取回 Mac：

```bash
rsync -av Jetson:jetson-llm-kernels/results/ <仓库目录>/results/
```
